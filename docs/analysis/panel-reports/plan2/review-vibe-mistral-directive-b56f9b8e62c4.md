# Review of plan 2 (commit 762acf3): sqlrepl model and export extension

Reviewed against the spec, `CLAUDE.md`, the code, the lab documents and results, and the live lab `repllab` (2022 CU27, 127.0.0.1:11980). Everything below marked "ran" was executed on the lab or in a scratch Go program under the working copy; nothing was simplified and no parameter the plan leaves out was filled in.

## Verified by running

1. **`checkSyncView`'s "text after the last `= 1`" reports a false filter problem on any clause containing the literal `= 1`.** Task 8 specifies the check as: after collapsing whitespace, "the text after the last `= 1` must be empty when `clause` is empty, and `and (<clause collapsed>)` otherwise". I created an article on my own `rv_z3k9q7_` publication (in a transaction rolled back in the same batch, `@@TRANCOUNT` 1 inside, 0 after) with the multi-line clause `a = 1\r\n  and b = 2`, called `sp_articlefilter` + `sp_articleview`, and read what the server wrote: the view is `... HAS_PERMS_BY_NAME(...)= 1  and (a = 1\r\n  and b = 2)` and `sysarticles.filter_clause` is the clause verbatim. Running the plan's algorithm on that real definition gives `view filter "and b = 2)", article clause "a = 1 and b = 2"` — a spurious `incomplete` finding on a view that matches. The plan's own unit cases and the lab's clause `Country = 'FR'` contain no `= 1`, so every test the plan writes passes; the defect appears only on a real filter such as `id = 1`, after all the code is written, as `incomplete` findings plan 3 would try to repair without converging. Boundary measured: multi-line clauses without `= 1`, and column names containing `]` or a space, pass; a column name containing a comma (`[a,b]`) mis-splits the column list, because the plan splits on every `,`.

2. **Task 10's `TestReadLabPullSubscription` cannot pass with the plan's own setup.** The plan's `testdata/pull-setup.sql` creates the publication with `@immediate_sync = N'false'` and then calls `sp_addpullsubscription @subscription_type = N'pull'` with no `@immediate_sync`; its own findings rule says "`immediate_sync` at the subscriber different from the publication: `incomplete`"; the test asserts "no finding under `publications[m_pp]`". I ran the setup verbatim (renamed `rv_z3k9q7_`): `Sales.dbo.syspublications` stores `immediate_sync = 0` for `rv_z3k9q7_pp`, while the subscriber's `rv_z3k9q7_psub.dbo.MSreplication_subscriptions` stores `immediate_sync = 1` (the parameter's default — the 2019 source inserts `@immediate_sync` verbatim, and `11-defaults` row 498 confirms default 1). So a reader built exactly as the plan says emits the `incomplete` finding the test asserts is absent. `lab/campaign/08-pull.sh` never hit this because its publication used `@immediate_sync = N'true'`, which matches the default. An implementer following the plan verbatim gets a red lab test at Task 10 Step 4 — after Tasks 3 to 9 are written — whose cause looks like a reader bug but is the setup.

3. **The ruling "`allow_partition_switch` alone stores `0x20`" is false; the bit values in Task 2 are right.** In transactions rolled back on the lab (`@@TRANCOUNT` checked, options restored to 0 afterwards) and at creation: `sp_changepublication`/`sp_addpublication` with `@allow_partition_switch = N'true'` alone sets `syspublications.options` to 96 (`0x60`) — allow=true also sets the replicate bit; then `@replicate_partition_switch = N'false'` leaves 32 (`0x20`); `@allow_partition_switch = N'false'` clears to 0. Setting replicate=true without allow is refused (21866). So `PubOptionAllowPartitionSwitch = 0x20` and `PubOptionReplicatePartitionSwitch = 0x40` are correctly decoded (verified), but the recorded measurement "allow alone stores 0x20, with replicate 0x60" is backwards, and the real rule — allow=true implies replicate=true — is exactly what plan 3's defaults table must record: a file with `allow_partition_switch: true` and omitted `replicate_partition_switch` would normalize replicate to the procedure default while the server stores true, a non-convergence only plan 3's convergence tests would catch. `sync_method` 5 and 6 were re-verified in the same rolled-back transaction: `database snapshot` stores 5, `database snapshot character` stores 6.

4. **The 2019 and 2025 parameter listings differ from 2022's, and the Task 12 rules do not cover the deltas.** I ran the Task 1 listing query on my own containers (started one at a time as `rv-z3k9q7`, removed afterwards): 2022 CU27 gives `R|TOTAL|316` with exactly the plan's 18 procedures and per-procedure counts; 2019 CU32 gives `R|TOTAL|307` — `sp_adddistributor` has only 4 parameters (no `@security_mode`, no `@multi_subnet_failover`; the 2019 source in `stored-procedures/sp_adddistributor.sql` confirms), no `@job_security_mode` on the four agent procedures, and `sp_addsubscription` lacks `@subscriber_login`/`@subscriber_password`/`@subscriber_security_mode`; 2025 CU10 gives `R|TOTAL|319`, adding `sp_adddistributor.@encrypt_distributor_connection`, `@host_name_in_distributor_certificate`, `@trust_distributor_certificate`. Task 12 maps `admin_link_security` to `sp_adddistributor @security_mode` and excludes `@job_security_mode`, but those parameters do not exist on 2019, so the mapping must be version-qualified or plan 3 cannot pass them there; and no Task 12 rule covers the 2025 trio, so `TestParametersCovered` fails at Task 13 Step 2 until someone measures that they store nothing readable (`sys.servers`/`sys.linked_logins` have no columns for them — checked on 2025). On 2019 the new fields' sources exist and behave the same: `job_login`/`job_password` in all three `MS*_agents` tables, `MSsubscriber_info` identical, `repl_distributor` linked login `uses_self_credential=0, remote_name='distributor_admin'`, `provider_string` NULL, and `sys.linked_logins` columns are identical to 2022's (`local_principal_id`).

5. **`commandSwitch` as described cannot pass its own `TestCommandSwitch` quoted case.** The plan says it "finds `-<name>` case-insensitively as a whole token, returns the next token with one level of `[...]` (with `]]` undoubled) or `\"...\"` removed", and the test asserts `-distributorlogin \"repl user\"` gives `repl user`. I implemented it with whitespace tokenization (`strings.Fields`) and ran it: the next token is `"repl`, the quote stripping never applies, and the result is `"repl` — the test fails. The plan never states that the tokenizer must treat a quoted string as one token. The other cases behave as specified on the lab's real command (`-Publisher [REPLLAB] -PublisherDB [Sales] -Distributor [REPLLAB] -Publication [SalesPub] -DistributorSecurityMode 1`): `DistributorSecurityMode`→`1`, `Distributor`→`REPLLAB`, `DistributorLogin` absent, `-PublisherDB` not matched by `Publisher`, `-Publication [a]]b]`→`a]b`. Cheap to find (Task 7 Step 4 fails immediately), but the plan should say "quote-aware tokenization".

## Concluded by reading

Hypotheses, not confirmed by running:

1. **Task 13 destroys the shared lab.** Step 1 runs `lab/start.sh 2019`, `2025`, `2022` and Step 6 runs `SHUTDOWN WITH NOWAIT`; `start.sh` does `podman rm -f repllab` and recreates the container. With four other reviewers using `repllab` concurrently, this task removes their container and all their in-flight `rv_` objects mid-session; the Global Constraints' "check `podman ps` before a lab step and start it if it is not running" contradicts a script that recreates. The 2019/2025 replays need a separate container (as the review rules already provide) or exclusive lab time. I did not run `start.sh`.

2. **Task 10's CLI path can never read a pull subscription on the single-instance lab.** The CLI opens only "every `-server` entry that is neither the publisher's nor the distributor's address"; on the lab, `-server repllab=tcp:127.0.0.1,11980` with `-publisher tcp:127.0.0.1,11980` equals both, so the entry is not opened, `Source.Subscribers` stays empty, and every pull subscription is exported publisher-side only with the `unreadable` finding. Only `TestReadLabPullSubscription`, which injects `Source.Subscribers` directly, exercises the connected path; the README's export command on `repllab` itself would report pull subscriptions as unreadable. The plan never says the reader may reuse the publisher connection when the subscriber name matches the publisher's `@@SERVERNAME`.

3. **"Every one of the 316 parameters covered by exactly one rule" is not literally true.** The Task 12 rules name only the non-obvious parameters; roughly 200 of the 316 (all article/publication field mappings, `@heartbeat_interval` → `distributor.properties[*]`, `@parameter_name`/`@parameter_value` → `agent_profiles[*].parameters[*]`, `@default`/`@profile_type`/`@description` of `sp_add_agent_profile`, `@logreader_job_name`, `@snapshot_job_name`, `@job_name`, `sp_addsubscription @subscriber_type`, …) are decided only by the "the fields of Tasks 3 to 10 hold them" clause. `TestParametersCovered` remains satisfiable on 2022, but the implementer must derive kinds for these from the model. Also the rule citing `no-column` for `@subscriptionlsn` is wrong: `11-defaults` row 415 maps it to `distribution.dbo.MSsubscriptions.subscription_seqno` (set only with initialize-from-lsn); `creation_only` is still the right kind because that window is runtime state, but the Reason's source is not.

4. **`subsetAllowed`'s test omits `character`**, which the spec explicitly allows for article subsets ("`native`, `character` or `database snapshot` sync"). An implementer treating the test's list as exhaustive would refuse a legal subset on a `character` publication.

5. **The three 2025-only `sp_adddistributor` parameters** (certificate/encryption of the distributor connection) are, by reading `sys.servers` and `sys.linked_logins` on 2025 (no columns carry them), probably creation-time flags — unmeasured, so Task 13 Step 2 stops on them ("reported, not invented") until measured; nothing in the plan says what they are.
