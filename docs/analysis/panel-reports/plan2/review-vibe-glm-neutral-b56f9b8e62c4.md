## Verified by running

The plan's TestReadLabPullSubscription setup creates publication `m_pp` with `@immediate_sync = N'false'` and then calls `sp_addpullsubscription @publisher, @publisher_db, @publication, @subscription_type = N'pull'` with no `@immediate_sync`; it asserts "no finding under `publications[m_pp]`", on the belief (Rulings and the finding list) that `independent_agent` and `immediate_sync` at the subscriber are "copies of the publication's values". | `SELECT immediate_sync FROM rv_qz4k2m_psub.dbo.MSreplication_subscriptions` | 1 |

`11-defaults` row `D.sp_addpullsubscription.pull.@immediate_sync` shows the same (stored 1 when the call omits the parameter; the parameter default is 1, not a copy), and `08-pull`'s `build()` only ever used `immediate_sync`-true publications, which is why the campaign never saw the disagreement. An implementer following the plan writes the `incomplete` check ("`immediate_agent` or `immediate_sync` at the subscriber different from the publication"), runs the plan's own setup, and gets a finding at `publications[m_pp].subscriptions[...]`, so the four expected `--- PASS` of Task 10 Step 4 cannot all arrive; the choices are to drop the `immediate_sync` comparison (or treat the stored 1 as the procedure default, not a copy), which is a decision the plan should make now. `independent_agent` has the same property for a secondary reason: `11-defaults` row 494 shows the omitted parameter always stores 1, so the same check misfires on any shared-agent publication even before plan 3 creates one.

Task 8's `checkSyncView`, as the plan specifies it, reports a mismatch on a view that is in perfect step, for any filter clause containing the substring `= 1` followed by more characters (`Amount = 10`, `Units >= 12`). The plan's algorithm is: collapse whitespace, take "the text after the last `= 1`" and compare it with empty or `and (<clause>)`. The last `= 1` of the whole definition then lands inside the clause itself. I implemented the algorithm exactly as written and ran it on the plan's own quoted lab definition of `SYNC_Customer` (whose text I confirmed verbatim on the lab with `OBJECT_DEFINITION`); with the view carrying the clause `and (Amount = 10)` and the article clause `Amount = 10`, the output is `[view filter "0)", article clause "and (Amount = 10)"]`, a false `incomplete` finding at `<article path>.sync_object`. The committed test cases (`Country = 'FR'`, `Country = 'DE'`, `Amount > 0`, an empty clause) all pass against the real definitions, so the committed tests cannot catch it; once plan 3 treats `incomplete` as a state it repairs, a publication whose filter says `Units >= 12` would be repaired on every plan and never converge. Cutting the tail after the `where HAS_PERMS_BY_NAME(...)` marker (or after the first `= 1` that follows ` from `) fixes it; `Amount > 0` style clauses are unaffected.

Task 6's expected lab values, Task 7's expected command strings and NULL accounts, Task 9's profile facts and Task 11's status values all measure exactly as asserted; see "Not a problem" for the list. No third verified defect: the remaining problems I found are textual and are in the next section.

## Concluded by reading

Task 10's CLI rule makes `-server` unusable on the very topology the plan tests on, and no committed test can catch it. The Rulings say "The export opens every subscriber named by `-server` with the same credentials as the publisher", but the Task 10 CLI bullet says "Every `-server` entry that is neither the publisher's nor the distributor's address is opened to `master` before the read and passed in `Source.Subscribers`". On the lab (publisher, distributor and subscriber on one instance, as `lab/setup.sql` builds it and as every integration test in the plan works), `-server repllab=tcp:127.0.0.1,11980` has the same address as `-publisher` and `-distributor`, so the entry is never opened and never reaches `Source.Subscribers`; the reader then produces the `pull_agent` nil `unreadable` finding whose message tells the user to "pass `-server %s=ADDRESS`", which the user has already passed and the CLI has just ignored. `TestReadLabPullSubscription` and `TestReadLabPullSubscriberNotConnected` both build the `Source` by hand (the first paragraph says so: "a connection opened for the flag key `repllab`"), and `TestServerFlags` only parses the flags, so the whole of Task 10 would go green while the feature the README update promises ("pull subscriptions are exported; `-server`") is unreachable through the command that the campaign's export guard, the byte-identical check of Task 11 and every future user will run. Opening every `-server` entry unconditionally (or mapping a coinciding entry to an already open connection) is a one-paragraph edit; after the code is written this is a user-visible failure that no test reports.

Task 10's subscriber query filter contradicts its own anonymous-subscription finding, and the spec requirement is the casualty. The query is specified as reading `[<subdb>].dbo.MSreplication_subscriptions` with `subscription_type = 1` among its qualifiers; the findings list of the same task says "a subscriber row of type 2: `out_of_scope` (anonymous, `08-pull` `P1.omitted`)". A type-2 row cannot pass a `subscription_type = 1` filter, so the query never returns it and the finding can never fire; at the publisher, the same anonymous subscription is stored as a named pull (`08-pull` `P1.omitted`: `publisher_subscription_type=1,subscriber_subscription_type=2`), so no other reading in Task 10 sees it either. The result is that plan 2, as specified, cannot detect anonymous subscriptions at all, while the spec requires the export to report them and plan 3 to refuse a database that has any ("Out of scope"). Worse, the reader would fetch nothing for that subscriber and classify the subscription `incomplete` ("no `MSreplication_subscriptions` row at a connected subscriber"), a state plan 3 repairs rather than refuses. Nothing in `08-pull` or `11-defaults` contradicts the type-2 finding itself; the fix is to lift the `= 1` from the SQL and let the Go code read every row of the publisher/db/publication, exporting type 1 and reporting type 2.

`sp_add_agent_profile @profile_type` and a handful of siblings are not covered by Task 12's mapping rules, so Task 12 must stall or improvise. I listed the parameters on the lab exactly as Task 1 prescribes: 316 rows, 18 procedures, and the per-procedure counts match the plan one for one; going the 316 against the rules, `sp_add_agent_profile`'s `@profile_type` is named by no rule (the rules cover only its `@profile_id`, as an output parameter) and no field of Tasks 3 to 10 holds it, and the plan's own gap rule then requires the implementer to "stop and report it, do not invent a field". The same status is one step softer for `@logreader_job_name` (`sp_addpublication`), `@snapshot_job_name`, the agents' `@job_name`, `@source_table` and `@vertical_partition` (`sp_addarticle`) and `@heartbeat_interval` (`sp_adddistributor`): a defensible mapping exists through fields the model already has (`job_name`, the source name, the columns, `distributor.properties`), but the rules never name them, so the implementer decides alone whether they are fields or exclusions. A sentence per group in the rules would remove the ambiguity; `@profile_type` needs a decision (a user profile is always custom, and the model never writes system profiles, so it reads like the `excluded` "not stored as configuration" family rather than a gap).

The concurrency hazard: `TestReadLabSales` asserts "two publications `SalesPub` and `SalesRef`" with "`Findings` empty", and Task 13 Step 5 runs the whole suite with "no `--- FAIL`" while other reviewers work on the same instance. During this review the lab carried `rv_q8n4az` (with a pull subscription at status 1) and `rv_c7m2xt_pp` (a full pull setup) inside `Sales`, and the current export emitted exactly the warning that such an object produces. This is a hypothesis about the environment, not a defect of the plan's design, but it is a repeatable way for the plan's committed tests to fail with no code change, and the plan's "one failed, the others passed" reading of every break step depends on a quiet lab the panel does not have. Worth a line in the plan: run the suite only on a lab whose `Sales` holds nothing but its own objects, or filter the asserted publication lists by name.
