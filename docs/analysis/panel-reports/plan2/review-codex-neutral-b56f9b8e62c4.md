## Verified by running

1. Task 12 classifies `@publisher` on every procedure except `sp_adddistpublisher` as excluded, calling it a non-SQL Server publisher parameter. The plan's own Task 10 setup passes `@publisher` to both pull procedures. On the running 2022 server, `SELECT o.name,p.name AS parameter_name,CASE WHEN OBJECT_DEFINITION(o.object_id) LIKE N'%IF @publisher IS NULL%' THEN 1 ELSE 0 END AS checks_null_publisher FROM sys.all_objects o JOIN sys.all_parameters p ON p.object_id=o.object_id WHERE o.schema_id=SCHEMA_ID(N'sys') AND o.name IN (N'sp_addpullsubscription',N'sp_addpullsubscription_agent') AND p.name=N'@publisher'` returned `sp_addpullsubscription|@publisher|1` and `sp_addpullsubscription_agent|@publisher|1`. Both procedures require the publisher name for an ordinary SQL Server pull subscription. A planner following the mapping would omit a required argument and fail to create pull subscriptions. Map both to `publisher.server`; the parameter coverage test must check the mapping's meaning, not just its presence.

2. The ruling and Tasks 7 and 10 read a pull agent's `job_login` from the subscriber's `MSsubscription_properties.job_login`. On the running 2022 Developer server, I ran `DECLARE @d nvarchar(max)=OBJECT_DEFINITION(OBJECT_ID(N'sys.sp_addpullsubscription_agent')); SELECT CASE WHEN @d LIKE N'%job_login = @cl_login%' THEN 1 ELSE 0 END AS stores_cl_login, CASE WHEN @d LIKE N'%@cl_login = @job_login%' THEN 1 ELSE 0 END AS assigns_cl_login, CASE WHEN @d LIKE N'%fn_MSrepl_editionid() = 32%' THEN 1 ELSE 0 END AS cloud_only, CASE WHEN @d LIKE N'%@job_login = @job_login%' THEN 1 ELSE 0 END AS passes_job_login_to_job`; it returned `1|1|1|1`. The procedure passes `@job_login` to job creation but stores `@cl_login` in that column, assigning it only for Cloud Lifter edition 32. `DECLARE @d nvarchar(max)=OBJECT_DEFINITION(OBJECT_ID(N'sys.sp_helppullsubscription')); SELECT CASE WHEN @d LIKE N'%job_login%sc.credential_identity%' THEN 1 ELSE 0 END AS help_uses_credential_identity` returned `1`. Thus a Windows pull agent with a job account exports `job_login: ""`, and plan 3 will miss or repeatedly plan an account change. The proposed lab test uses a null account, so it cannot expose this. Read the job step's proxy credential with the same visibility handling as `run_as`.

3. Task 8's `checkSyncView` locates the filter after the *last* `= 1` and collapses whitespace in the whole definition and clause. I ran a small Go reproduction of those exact operations against the quoted view shape: a matching `and (Flag = 1)` produced `last-equals-one suffix: ")"`, while `and (City = 'New  York')` and `and (City = 'New York')` produced `distinct literals collapse equal: true`. Following the plan would report a valid `Flag = 1` view as incomplete and miss a real change to spaces inside a string literal. Locate the permission guard structurally and compare the SQL clause without normalizing literal contents.

## Concluded by reading

1. Hypothesis: Task 10's CLI rule opens a `-server` entry only when its address differs from the publisher and distributor addresses, yet the lab pull subscriber is that same server and `Source.Subscribers` is the only stated route to its subscription tables. If the implementation simply skips the entry, `TestReadLabPullSubscription` cannot pass and same-instance pull subscriptions get an `unreadable` finding. The task should explicitly put an existing connection into `Subscribers` under the normalized subscriber name when addresses coincide.

2. Hypothesis: the collision suffix for secret names is assigned in reading order (`_2`, `_3`), while agent queries such as `qSnapshotAgents` and `qDistributionAgents` have no `ORDER BY`. Two distinct login sources that sanitize to the same name could exchange secret names between exports or when another object is added. That would break the export's stable-file guard and could make a desired file refer to the wrong environment variable. Derive a stable suffix from the unsanitized source, or sort all sources before assigning names.
