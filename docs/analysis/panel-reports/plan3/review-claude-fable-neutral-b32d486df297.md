## Verified by running

1. Extending a pull subscription, or a "replication support only" subscription, with the call the plan describes breaks the subscription and makes the next plan refuse. Task 11 and Task 12 write the extension as `sp_addsubscription @article = N'<name>'` (or `N'all'`), and R15 passes a parameter only when it differs from the context default, plus the identity parameters; `@subscription_type = N'pull'` is "always passed" only for the creation calls. I replayed exactly that on a publication without `immediate_sync` (`native`, `independent_agent` true, `allow_pull` true) with a pull subscription created by the plan's three calls: `EXEC sp_addarticle @publication = N'rv_cfableq7m2_pp', @article = N'rv_t2', @source_owner = N'dbo', @source_object = N'rv_t2';` then `EXEC sp_addsubscription @publication = N'rv_cfableq7m2_pp', @article = N'rv_t2', @subscriber = N'repllab', @destination_db = N'rv_cfableq7m2_s2';`. The server accepted it, printed "The distribution agent job has been implicitly created", and left `syssubscriptions` with `rv_t1` at `subscription_type` 1 and `rv_t2` at `subscription_type` 0, plus a second row in `MSdistribution_agents` for the same subscriber database (`...-2052` type 1, `...-2053` type 0) with a running push job. The same call on a subscription created with `@sync_type = N'replication support only'` gave rows `rv_t1..rv_t3` at `status 2, sync_type 2` and the new `rv_t4` at `status 1, sync_type 1`. The export then reports, for both, `incomplete: ... articles disagree on subscription_type, sync_type, update_mode or loopback_detection`, which is the very finding Task 15 `TestBuildRepairsIncomplete` refuses with "repair of this state is not measured". So one `apply` of "add an article" on such a publication leaves a state that `plan` refuses for good. No unit or lab test extends a pull or a non-snapshot subscription (`TestLabPullSubscription` only creates and drops). The plan must say what the extension, the subset addition and the intermediate-state completion pass for `@subscription_type` and `@sync_type`, or refuse them, and test it.

## Concluded by reading

1. Hypothesis: the cost rules cannot produce the costs the tests and the spec ask for when an article or a subscription is added. The table gives `add_article` the class `snapshot`; Task 9 says class `snapshot` costs "R11's", that is `full_generation_deferred` when ready and `immediate_sync` is kept, `online` otherwise; R11 says such a change "marks nothing", which R10 contradicts for `sp_addarticle` (a status 1 row on every subscription). Yet `TestAddArticleImmediateSync` expects `[new_snapshot]` on ready `SalesPub`, while `TestSnapshotClassCost` expects `full_generation_deferred` for `alt_folder` in the same class and the same state: both cannot come from the class. `TestLabAddArticle` expects `new_snapshot` on a publication without `immediate_sync`, where `add_article` gives `online` and `extend_subscription` is `online` too. `add_subscription` and `extend_subscription` are `online` with cites `06-structural C1.*`, `C2.*`, `C5.*`, which are drops; the spec costs an extension "snapshot of the new article" and a new snapshot-initialized subscription obviously needs a generation that locks the tables under `native`. `new_snapshot` is not in the list of "a strategy's own costs" either. Either the tests fail or the implementer invents the rule; the cost line is the product's main output (anti-goal 1).

2. Hypothesis: secret names are compared, and they should not be. The cost table has entries for `...connection.password_secret` of the log reader, snapshot and distribution agents (`sp_change* @publisher_password`, `subscriber_password`), `notCompared` (Task 10) does not list any `*_secret` path, and the spec says "`plan` cannot read them, so it never plans a password change" (`apply -rotate-secret` is plan 4). The export derives each name from the server and login (`internal/reader/secrets.go`; today `admin_password_secret: SQLREPL_SQL_REPLLAB_DISTRIBUTOR_ADMIN`). A file that names its secret otherwise gets a password change planned at every `plan`, forever, and a hand-written `distributor` section on an existing distributor that omits `admin_password_secret` is either refused by rule 5 (no measured default) or by "cost not measured". `TestBuildSecrets` uses the derived name, so nothing shows it.

3. Hypothesis: normalization rule 5 does not say what happens to nil nested objects, and the literal reading breaks the export round trip. `11-defaults` holds `D.sp_addpublication.transactional.@ftp_port` 21 and `@ftp_login` `anonymous`; the export writes no `ftp` block when `enabled_for_internet` is false. "Defaults for every nil property of a declared object" fills `snapshot.ftp.port` and `.login` in the desired side, the current side has none, and `ftp.port` has no cost entry: the unchanged export would be refused, or `TestNormalizeExportUnchanged` fails on "deep-equal to itself". The same question holds for `backup`, `pull_agent`, `distributor_connection`. The rule needs the `OmittedOK` conditions of `internal/model/path.go` stated.

4. Hypothesis: a declared schedule cannot be written the way the convergence files write it. The scenarios declare `frequency: once`, `start_date: 99991231`; `Schedule` fields are plain values and the export of the agent I created with `@frequency_type = 1, @active_start_date = 99991231` reads `enabled: true, frequency: once, start_date: 99991231, end_date: 99991231, end_time: 235959`. Compared in full, the file's `enabled: false`, `end_date: 0`, `end_time: 0` differ, so every second plan carries a `sp_changepublication_snapshot`; `enabled` has no parameter in that call at all, and the plan has no rule (refusal or operation) for a file whose schedule is disabled. Cheap to fix in the files, but the `enabled` case is a missing rule.

5. Hypothesis: the `allow_push` to false drop and re-add (Task 13, table entry `DropReadd` 20012) is unreachable or wrong. Rule 7 of Task 6 already refuses a push subscription on a publication with `allow_push` false, and re-adding push subscriptions after the change would get 20012 again. What remains is a file without the push subscriptions, where step 4 drops them anyway and the change is a plain step 6 call. No test covers it.

6. Hypothesis: several snapshot-publication changes are measured and still refused. The table is "transactional unless said otherwise", and `replicate_ddl`, `allow_pull`, `allow_partition_switch`, `allow_drop`, `status`, article `status` and `fire_triggers_on_snapshot` cite no `SNAP.*` row although `09-snapshot-pub` has them (`SNAP.P03`, `P04`, `P08`, `P10`, `P11`, `A14` to `A16`, `A19`, all `ok`). If `PubType` is `transactional` there, a snapshot publication cannot change its description's neighbors; if it is `""`, the entry applies with no row of that type behind it. The table should say which.

Three smaller hypotheses left out (the order of parameters in `TestCreationCallPassesOnlyNonDefaults` against `model.Parameters`, a second schedule on a current agent that the file does not list, R24 against the spec sentence that `plan -sql` lists `apply`'s `sp_update_job` calls).
