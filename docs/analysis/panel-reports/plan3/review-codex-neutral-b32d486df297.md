## Concluded by reading

1. Hypothesis: Task 18 opens subscribers named in the desired file before `reader.Read`; Task 12 must drop pull subscriptions that are present only in the current state. When a user removes the last pull subscription from the file, its subscriber is absent from the desired names, so `readPullRow` records its agent as `unreadable` (`internal/reader/agents.go`) and no subscriber connection exists for `sp_droppullsubscription`. R29 refuses operations on an unreachable pull subscriber, but it never attempts this reachable, current-only one. The plan needs to discover current pull subscriber names before deciding connections, or the whole-truth deletion cannot run.

2. Hypothesis: R6 and Task 14 decide whether to drop an absent user profile solely from current `Facts.ProfileUses`. If the file drops the sole publication or subscription using that profile, its current use prevents the profile drop in step 11, even though step 5 or 9 removes the user. The first apply leaves a now-unused profile that the next plan will drop, violating convergence and the spec's shared-object rule. `TestProfileDropOnlyUnused` covers a currently used profile and an already unused one, but not a use removed by this same plan.

3. Hypothesis: R24 explicitly omits snapshot-job disable/restore and `sp_start_job` from plan operations and `-sql`, leaving them to plan 4. The spec's `apply` step 3 explicitly says that `plan` lists its `sp_update_job` and `sp_start_job` calls with the other operations, including in `-sql`; the anti-goal requires the printed T-SQL to be the executed T-SQL. If implemented as written, the generated SQL omits server-changing calls that apply will execute, so the DBA cannot review the full plan and the GUI/JSON plan cannot represent it. Plan 4 cannot repair that promise without changing plan 3's operation and rendering contract.

4. Hypothesis: Task 9 says `finish` assigns the `Snapshot` class the R11 cost of `full_generation_deferred` when a snapshot is ready, while Task 7 gives `add_article` that class and Task 11's `TestAddArticleImmediateSync` requires `new_snapshot`. The measured row `15-snapshot-scope C.native.addarticle` has `ready_before=1` and `f10`; the call is accepted and creates a status-1 row for the new article. A literal implementation of `finish` fails Task 11, or worse, labels that pending new-article delivery as a deferred full generation. The plan needs an explicit operation-specific cost rule rather than relying on the class alone.

5. Hypothesis: R21 refuses creating a subscription with `initialization: lsn` until a precondition exists, but no task in plan 3 implements that check and the handoff to plan 4 does not assign it. The spec includes LSN initialization and specifies the check because a wrong LSN can be accepted while stopping subscriptions of the publisher database. Following this plan leaves an in-scope initialization mode permanently refused despite the measured `10-init-modes` cases and provides no route to the required validation.

## Not a problem

- The proposed `sp_addarticle` creation call with only its four identifying parameters works on an isolated `rv_7c4e19` publication.
