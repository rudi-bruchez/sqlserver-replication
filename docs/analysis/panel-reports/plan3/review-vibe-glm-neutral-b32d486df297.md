# Review of plan 3, `docs/superpowers/plans/2026-11-12-sqlrepl-3-planner.md` (c8c06e3)

Reviewed against the spec, `CLAUDE.md`, plan 2, the `internal/model`/`reader`/`state`/`decode`/`cmd` code, the measured tables of `lab/results/2022/` and the lab itself. Everything replayed on the lab used objects named `rv_zq34k8*`, inside rolled-back transactions except where a refusal made that impossible; all of them are removed (see the end of the report).

## Verified by running

**1. Task 11's and R15's rules, followed literally, generate a refused `sp_addarticle` for every filtered article: `@filter` pointing at a procedure that does not exist yet is error 14027.** Task 11 pins only one exclusion: "`sp_addarticle` from `creationCall`, never with `@filter_clause` (lab row 12)". But `model.Parameters` also maps `@filter` and `@filter_owner` to `articles[*].filter.procedure` (kind `field`, `internal/model/parameters.go`), the defaults it consumes hold rows for them (`D.sp_addarticle.table.native.@filter|0`, `@filter_owner|0`, results that are values, not `no-column`), rule 2 of Task 6 requires `filter.procedure` of a declared filter, `TestEncodersCoverParameters` demands an encoder for every `field` entry, and `neverPassed` covers only `job_name` and `creation_only` parameters of objects the plan does not create. So `creationCall`, keeping "a parameter ... only when its normalized value differs from the default of its context" (R15), passes `@filter = N'm_flt1'` for the article of `TestLabCreatePublication`, whose procedure `setup.sql` never creates (it is created later by `sp_articlefilter`). Replayed on the lab, in a rolled-back transaction on `rv_zq34k8_c`:

```
EXEC sp_addarticle @publication = N'rv_zq34k8_cp', @article = N'rv_zq34k8_c',
     @source_object = N'rv_zq34k8_c', @filter = N'rv_zq34k8_flt', @filter_owner = N'dbo';
--> sp_addarticle with @filter: ERR 14027: [dbo].[rv_zq34k8_flt] does not exist in the current database.
    (followed by Msg 20026 from sys.sp_MSreinit_article inside the refused call)
```

An implementer following the plan hits 14027 in the central convergence scenario (Task 19, step 2's "Runs"), after Tasks 5 to 18 are built. The fix is the same exclusion the plan already pins for `@filter_clause`, stated for `@filter` and `@filter_owner`.

**2. The plan never decides `@vertical_partition`, and its column-creation rule is only correct for one of the two possible readings; the other publishes just the primary key column.** Task 11 says: "for columns, one `sp_articlecolumn @operation = N'drop'` per column absent from `columns`", and Task 19 pins that call ("`sp_articlecolumn` (`b`, `drop`)"). That flow is correct only when `sp_addarticle` was called without `@vertical_partition = N'true'`. But `model.Parameters` maps `@vertical_partition` to `articles[*].columns`, and the measured default row (`D.sp_addarticle.table.native.@vertical_partition|2/2`, "rows of the article / columns of the table") is a ratio, not a value the `Defaults` structure can express, so the plan leaves the parameter's treatment open; R15's keep-when-non-default rule, applied to a declared column subset (a subset differs from the default "every column", R30), is exactly the reading that passes it. Replayed on the lab, all inside one rolled-back transaction:

```
EXEC sp_addarticle @publication=..., @article=N'rv_zq34k8_t',
     @source_object=N'rv_zq34k8_t', @vertical_partition=N'true';
--> published columns: [id]        (table rv_zq34k8_t: id PK, a, b)
EXEC sp_articlecolumn ... @column=N'b', @operation=N'drop';
--> published columns: [id]
EXEC sp_articleview ...             (no @filter_clause)
--> view syncobj_0x...: [id]
```

With `@vertical_partition` not passed, the same sequence yields a view over `[id, a]` (verified, both flows). So the combination the plan's rules generate when columns are declared (`@vertical_partition = N'true'` from `creationCall`, then drops) leaves every non-key column unpublished: every call is accepted, the configuration converges except that a new plan again sees the missing column, and the subscriber silently receives only the key column of a filtered article, the anti-goal 3 failure the spec exists to prevent. It is caught only by the data assertion of `TestLabCreatePublication`, where it will look like an encoder or default bug, not an ordering bug. The plan needs one sentence: `@vertical_partition` is never passed (or passed false) at creation, the article starting from all columns and dropping.

**3. `TestSubsetRules` (Task 12) names the wrong error for the lab fixture: an `immediate_sync` + `concurrent` publication (the `SalesPub` configuration) refuses a named subscription with 14100, not 14122.** Replayed on the lab, on publications of my own built to match each half:

```
imm+concurrent: ERR 14100: Specify all articles when subscribing to a publication using concurrent snapshot processing.
imm+native:     ERR 14122: The @article parameter value must be 'all' for immediate_sync publications.
```

14122 is the `immediate_sync` + `native` error (`D.imm_native.extend_rule`); the concurrent-family error is 14100 (spec "Subscriptions", O8). Task 12 Step 1 says "a subset on `SalesPub` (`immediate_sync`) is refused by normalization (14122)" while rule 7 of Task 6 only says "(14100 or 14122)". As written the test cannot pass against a correct implementation, or it forces the wrong number into the refusal the user sees on every `concurrent` publication; the rule needs the case split the lab shows.

**4. Task 3's `PF.set_default` sends the implementer to a source that cannot do the job: `sp_change_agent_profile` accepts only `description`.** The task says: "the procedure and property the 2019 sources in `stored-procedures/sp_change_agent_profile.sql` use to make a profile the default of its type; read the source and name them". That 2019 source, and the 2022 CU27 definition on the lab, contain:

```
IF lower(@property ...) not in ('description') RAISERROR(21183, 16, -1, @property)
```

No `default` property exists in either version. In the 2019 folder, the only procedures that write `def_profile` are `sp_add_agent_profile` (at creation, `@default`) and `sp_drop_agent_profile`; on the lab, `def_profile` is additionally written by the internal `sys.sp_MSupdate_agenttype_default`, which no public procedure wraps. So the case cannot be written from the cited source, and `agent_profiles[*].default` (compared by the reader, dropped by R6's step 11, listed in the cost table's `19-profiles PF.*` entries) either gets an ad hoc call to an internal procedure that nothing measured, or no cost entry at all and every `default` change becomes an unmeasured refusal. The measurement task needs a different instrument or the case needs to become a refusal with the reason.

**5. A snapshot publication accepts `database snapshot` and `database snapshot character` at creation; only `concurrent` is refused (22547). So Task 2's `snapshot-pub dbsnap_c` context is measurable, contradicting Task 6's refusal list.** Replayed in rolled-back transactions:

```
dbsnap on snapshot pub: accepted
dbsnap_c on snapshot pub: accepted
concurrent on snapshot pub: ERR 22547: A concurrent snapshot is not allowed for snapshot publications.
```

Task 6 rule 5 says a nil property with no measured default is refused "(the `dbsnap_c` and snapshot `concurrent` contexts among them)", which describes the state of `lab/results/2022/` before Task 2 runs but is stale the moment Task 2 produces the very rows Task 5 consumes ("every `nondbo` context of Task 2", listed for `native, character, concurrent, concurrent_c, dbsnap, dbsnap_c` and the `snapshot-pub` variants). An implementer who follows rule 5's parenthetical refuses articles of a measured context, or ships a defaults table and a normalization rule that disagree; the parenthetical should name only `snapshot-pub` + concurrent, which cannot be created and measured at all.

**6. `sp_articleview` with no `@filter_clause` is required to build the view of a column-filtered article, which Task 11 forbids and Task 19 expects.** Task 11: "`sp_articleview` is never called without the article's clause" (echoing the spec, which derives the ban from `14-filter-view F4`, the case where a filter procedure keeps filtering while the view goes unfiltered). Replayed on the lab: after `sp_addarticle @vertical_partition='true'` and `sp_articlecolumn` the article has no view (its `sync_objid` still names the source table), and `sp_articleview @publication, @article` with no clause creates `syncobj_0x...` over exactly the published columns, leaving `filter = 0`, `filter_clause = NULL`, nothing diverging. Task 19 pins the call in its asserted sequence ("`sp_articlecolumn` (`b`, `drop`), `sp_articleview`") for `m_t2`, which declares no filter. The sentence needs its `F4` scope (an article that has a filter procedure), or the clause-less articles of Task 19 cannot be created at all.

## Concluded by reading

**1. "(today = the day of the run)"`). My live export of `Sales` today carries `start_date: 20261112` on both snapshot agents, i.e. the day `lab/start.sh` was last run. Once the fixture is committed by Task 4, any later `start.sh` (which the lab README uses to reset the accumulating residue) moves the live `start_date`, and the two live empty-plan tests, whose whole point is zero operations (Review Focus 1), plan a phantom `sp_changepublication_snapshot` schedule change and fail. **2.
