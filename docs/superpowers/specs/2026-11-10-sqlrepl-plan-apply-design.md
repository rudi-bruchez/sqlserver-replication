Design of the declarative engine of `sqlrepl`: describe a SQL Server replication in a file, see what it takes to get there, and get there. ## Intent

Setting up SQL Server transactional replication means chaining a dozen system procedures (`sp_adddistributor`, `sp_adddistributiondb`, `sp_adddistpublisher`, `sp_replicationdboption`, `sp_addlogreader_agent`, `sp_addpublication`, `sp_addpublication_snapshot`, `sp_addarticle`, `sp_articlefilter`, `sp_articleview`, `sp_addsubscription`, `sp_addpushsubscription_agent`…) in the right order, with parameters whose interactions are documented badly or not at all. Changing an existing replication is worse: each change may silently need a new snapshot or a reinitialization of the subscriptions, and Microsoft Learn is wrong on several of them (measured, analysis section 5).

`sqlrepl` lets a DBA describe the replication they want in one YAML file, and does the procedures for them. The first situation it serves is creating a replication from nothing. The second is changing an existing one, adding or removing articles, changing filters or properties, each time by the least costly path the measurements allow.

The tool is a single Go binary, `sqlrepl`. It replaces the configuration layer only: Microsoft's replication engine (log reader, snapshot and distribution agents) keeps doing the replicating.

## Where this sits in sqlrepl

`sqlrepl` is meant to analyze, plan, apply and monitor. This design covers the engine: `export` (exists), `plan`, `apply`, and `snapshot` with its report (see "Snapshot runs and their report"). Each of the following gets its own design later, in this order:

1. a local web GUI, served by `sqlrepl` on localhost: creation wizard, editing of an existing configuration with the cost of each change shown while editing, review and apply of a plan, monitoring view;
2. monitoring: agent status, latency (tracer tokens), undistributed commands, agent errors;
3. data validation between publisher and subscriber;
4. configuration audit (risky settings);
5. performance analysis.

The engine must be built so that the GUI is a front end on it, not a second implementation (see "Engine as a library").

## Goals

- Create a complete replication from one file: distributor (local or remote), publication database, publications, articles, filters, subscriptions and their agents.
- Change an existing replication by editing the file: add, change or drop any object the file describes.
- Show, before anything runs, the exact operations, the exact T-SQL, and the cost of each operation.
- Converge: after a successful `apply`, `plan` on the same file finds nothing to do, and the data at the subscriber is what the file describes.

## Scope

In scope:

- transactional publications and snapshot publications;
- push and pull subscriptions, initialized by snapshot, by "replication support only" (data already in place), from a backup, or from a log sequence number;
- the distributor: creation if missing, local or remote, its retention and its snapshot working directory;
- agents: log reader, snapshot, distribution (independent and shared), their schedules, profiles and security, including Windows job accounts;
- user-defined agent profiles;
- SQL Server 2019, 2022 and 2025, as publisher, distributor and subscriber. Other versions are refused with a clear message. The support claim for a version holds once the measurement campaign has run on it.

Out of scope: merge replication, peer-to-peer, updatable subscriptions (immediate or queued), anonymous subscriptions, non-SQL Server publishers or subscribers. The export reports them under `warnings`; `plan` refuses a database that has any, rather than dropping what it cannot model.

## Non-goals

- Uninstalling the distributor. The file never causes `sp_dropdistributor` or `sp_dropdistributiondb`.
- Moving a publication database to another distributor. A file that names a different distributor from the one in place, or a remote one where it is local, is refused by `plan` with the reason: the move means `sp_dropdistributor` at the publisher, which removes every publication. My call.
- Creating or changing the schema of published tables, or the subscriber databases themselves. They must exist; `plan` checks it and says so.
- Creating the snapshot folder on disk. `plan` checks what it can (`xp_fileexist` or equivalent at the distributor) and warns.
- Rolling back a partly applied plan (see "Apply").

## Anti-goals

These four make `sqlrepl` a failure even if it works. Each is a hard rule for the builder, with the mechanism that enforces it.

1. A hidden reinitialization or snapshot. Every operation that invalidates a snapshot, reinitializes subscriptions, or drops and re-adds subscriptions is marked in the plan, with the publications, articles and subscriptions it affects. `apply` repeats the count of such operations in its confirmation question.
2. Opaque T-SQL. `plan -sql` prints the T-SQL that `apply` will run, statement by statement and server by server, identical except for secret values (see "Secrets"), and `apply` logs each statement before running it. There is no other code path that changes the servers.
3. Silent divergence between publisher and subscriber. The engine never generates a configuration known to diverge without error. Known cases, each with its rule in "Strategies": a row filter given only as `sp_addarticle @filter_clause` (lab row 12); a synchronization view left on an old filter or column list (panel); a subscription re-added with `@article = 'all'` that comes back active without its data (panel); a subscription dropped and re-added without snapshot initialization while changes were being made (panel).
4. Unannounced loss of subscriber data. Operations that delete or replace data at the subscriber are marked as such: a reinitialization of an article whose `pre_creation_cmd` is `drop`, `delete` or `truncate`, and a change of `pre_creation_cmd` itself. Dropping an article or a subscription leaves the subscriber table in place, and the plan says so.

## The file

### Unit and format

One file describes one publication database: its distributor, its publications, their articles and subscriptions, and its agents. Several databases are several files. The format is the YAML of the existing export (`internal/model`), extended (see "Extending the model and the export"). `sqlrepl export` gives the starting file of an existing replication; for a new one, the user writes it (later, the GUI wizard writes it).

### The whole truth

The file is the whole truth for its publication database. A publication, article, subscription or agent schedule of that database that exists on the server and is not in the file is dropped by the plan, and the plan marks drops like any other cost. Objects shared with other databases follow the rules of "Shared distributor objects".

### Omitted properties

A property left out of a declared object means the SQL Server default: the value the `sp_add*` procedure stores when the parameter is not passed. If the server holds another value, the plan changes it back.

Defaults are not one value per property. They depend on the context of the object, measured by the panel:

| Object, context | Default measured (2022 CU27; same on 2019 CU32 and 2025 CU10 where checked) |
|---|---|
| table article, transactional publication, `native` or `concurrent` | `schema_option 0x30073`; commands `CALL [dbo].[sp_MSins_…]`, `SCALL [dbo].[sp_MSupd_…]`, `CALL [dbo].[sp_MSdel_…]` (an unqualified procedure name in a command is stored with `[dbo]`, even for a source table in another schema, `11-defaults` context `table.non-dbo-schema`: the file writes the schema it means, and the reader compares against the stored one); destination owner: the source schema (`sales.S1` gives `sales`); status 16 (parameterized); `pre_creation_cmd` drop |
| table article, transactional publication, `character` | `schema_option 0x30073`; commands `SQL`; destination owner NULL |
| table article, snapshot publication | `schema_option 0x30071`; commands `SQL`; destination owner under `native`, the default method of a snapshot publication (`D.sp_addpublication.snapshot.@sync_method` 0): the source schema (`D.sp_addarticle.table.snapshot-pub.@destination_owner`, a `dbo` source, and a table of the schema `rv_s`, panel GLM, `O16`); under any other method not measured, and refused as such (a view under `character` on a snapshot publication stored NULL, fix review, `O16`) |
| schema-only article (view, procedure, function), by `sync_method` | `schema_option 0x1`; `pre_creation_cmd` drop; status 16; destination owner, on transactional and snapshot publications alike: under `native`, the source schema (`11-defaults` `D.sp_addarticle.view-schema-only.@destination_owner` and its `proc` and `func` twins, on a `native` publication with `dbo` sources, which alone cannot tell the source schema from `dbo`; a view, a procedure and a function of a non-`dbo` schema, fix review; a view and a table, controller; a view and a procedure of the schema `rv_s`, panel GLM, whose report does not give the method; all `O16`); under `concurrent` and `database snapshot`, the source schema (a view, fix review, `O16`); under `character` and `concurrent_c`, NULL (a view, a procedure and a function, fix review, and under `character` a view on a snapshot publication too; under `character` a view and a table, controller; all `O16`), as for a table article under `character`; under `database snapshot character`, not measured, and refused as such |
| publication | `sync_method native`, `retention 336`, `independent_agent 0`, `immediate_sync 0`, `allow_push 1`, `allow_pull 0`, `replicate_ddl 1`, `allow_subscription_copy 0`, `allow_initialize_from_backup 0`, `snapshot_in_defaultfolder 1`, `status inactive` |

The table is a sample: the complete defaults, for every parameter of every in-scope procedure, are the rows `D.<procedure>.<context>.<parameter>` of `11-defaults` and, for the distributor procedures, of `distributor-defaults`. A value printed `pre-existing(...)` in those files was in place before the call and is not a default. The default of `sp_addsubscription @subscriber_type` is not measured (the lab's subscriber is registered beforehand, `D.sp_addsubscription.push.@subscriber_type`); the builder leaves it out of the defaults table, so a file that omits it is refused as unmeasured until the campaign measures it. The consequence is wide: until then, a hand-written subscription must state the subscriber type. Item 19 measures it in one call, on a fresh subscriber that is not registered yet. The builder's defaults table is keyed by object type and by the properties the default depends on (publication type, `sync_method`, article type), each entry with its source. Where a property requires another, an omitted prerequisite takes the value the declared property requires, not the procedure default: `immediate_sync` needs `independent_agent` (`sp_addpublication @immediate_sync = 'true'` alone is refused with 21022 and does not fill it, panel), a pull subscription needs `allow_pull` and a push subscription `allow_push` on its publication (`sp_addsubscription` returns 20012 otherwise, panel). Otherwise a short file would normalize to a combination the server refuses.

Three properties have no default and must be written in the file: `status` of a publication, `initialization` of a subscription, and the name of a row filter's procedure (`sp_articlefilter` refuses a NULL `@filter_name`, 14043; the engine never invents one, and never falls back on `sp_addarticle @filter_clause`). My call. The procedure default for `status` is `inactive`, and a short hand-written file applied to an active publication would deactivate it with a cost the plan would present as online (panel).

The export keeps writing every property, so that an exported file is explicit.

### What is not compared

- Names that replication generates: job names, generated synchronization views (`syncobj_0x…`), generated command procedures when the file does not name them.
- Values derived from other properties: article status bits `0x8` and `0x20` when `schema_option` has `0x8` (lab row 3).
- Runtime state: subscription status, `immediate_sync_ready`, history, and the `active` bit (`0x1`) of an article's status, which no procedure sets and the generation of a snapshot sets, before and without any delivery (`15-snapshot-scope` `E.generated_undelivered`; panel Mistral, `O1`, on a `character` publication whose subscriber table did not exist). These are not compared, and the plan reads them as observed facts (see "Inputs"), never as a witness of a delivery.
- Schedule dates and times set at creation (`start_date` is the creation day) when the file does not declare a schedule. A schedule left out of the file means the schedule the procedure creates (daily every 5 minutes for a snapshot agent, `11-defaults` `D.sp_addpublication_snapshot.transactional.@frequency_*`; continuous for the distribution agent of a push subscription, `D.sp_addsubscription.push.@frequency_type` 64), compared on its frequency fields only. A declared schedule is compared in full.
- The agent command line (`command`). The export shows it for information, the plan ignores it, and warns when it carries parameters beyond those the procedures generate; agent tuning belongs in profiles. My call.
- The existence of a shared distribution agent: it is created with the first subscription that uses it and disappears with the last, its job with it (`07-changes` `SHR.after1`, `SHR.after2`); its properties are compared while it exists. My call.
- The `initialization` of an existing subscription. It is a creation parameter: it decides how the subscription is created, and how it is re-created when a plan must drop and re-add it. Changing it alone plans nothing, with a note.

### Names

Server names are compared case-insensitively (`syssubscriptions.srvname` is stored in upper case). Command procedures are always written by the engine schema-qualified, in `sp_addarticle` and in `sp_changearticle` alike: the two procedures store an unqualified name differently (`sp_addarticle` qualifies it with `dbo`, `sp_changearticle` keeps it unqualified, panel, on 2022 and 2025), so passing the file's text through would never converge. Normalization qualifies an unqualified name in the file with the schema `sp_addarticle` would use (`dbo`, whatever the schema of the source table: for a table of the schema `m_s`, `CALL m_ins` is stored as `CALL [dbo].[m_ins]` and the generated procedures are `[dbo]`-qualified too, `11-defaults` `D.sp_addarticle.table.non-dbo-schema.*`).

## Shared distributor objects

The distributor serves other publication databases the file does not see. For the objects that belong to the distributor rather than to the database (Rudi's decision):

- the distributor, the distribution database, its retention, the `MSdistributor` properties and user agent profiles can be created and changed by the file;
- they are never dropped while something uses them. A user profile is dropped only when it is absent from the file and no agent of any database at that distributor uses it; which profile is the default of its agent type is a distributor-wide setting;
- a change to a shared object is marked "shared" in the plan, with the list of the other publication databases the distributor serves. Two files that disagree on a shared value therefore each show the change as shared when they are planned; `plan` cannot see the other file, so it reports the conflict by showing that the server's value differs from what this file wants on a shared object. My call on the mechanism.

The reader must read every profile of the distributor and which agents use it, not only those used by this database (today `collectProfiles` reads only the latter, panel).

## plan

`sqlrepl plan -f desired.yaml` reads the current state, normalizes the desired file, compares them, and prints the plan. It runs only `SELECT` statements and read-only checks.

### Inputs

The comparison takes three inputs: the desired configuration, the current configuration (the reader's `model.Config`), and the observed runtime facts the costs depend on: per subscription its status and the articles it actually covers, per publication whether a snapshot has been generated and is still valid (`immediate_sync_ready`), whether a snapshot is pending, and per distribution agent its state (running or stopped, and its last error since the latest generation of the publications it serves), which the warning below needs. My call: the measured costs depend on these facts (analysis section 5), so they are an explicit input rather than a guess; the GUI supplies them the same way.

A snapshot is pending when a subscription awaits a run of the snapshot agent: a subscription not yet initialized, a subscription marked for reinitialization, or a subscribed article that no run has generated yet. `syssubscriptions.status` 1, or a subscribed article whose `sysarticles.status` lacks the active bit `0x1`, shows it. Both are set by the generation, not by the delivery, in the two contexts measured. On a `character` publication without `immediate_sync`, with the distribution agent stopped, a run set the new article's subscription to status 2 and its active bit while nothing reached the subscriber, and the delivery came only when the agent was started (`15-snapshot-scope` `E.extended`, `E.generated_undelivered`, `E.delivered`). On a `database snapshot` publication with `immediate_sync`, the agent was running and its delivery of the new article failed, and the subscription still ended at status 2 (round 1 results, `git show 8db6060:lab/results/2022/15-snapshot-scope.txt`, `A.imm.dbsnap`). `sp_addsubscription` on an `immediate_sync` publication with a ready snapshot also sets status 2 at once, with nothing delivered (`05-snapshot-flag` `S7`). These columns therefore show what awaits a generation, and a generated but undelivered snapshot reads as delivered. The first version of this definition said that only a delivered snapshot sets the active bit; `E.generated_undelivered` contradicts it. The pending definition therefore decides one thing only, whether a generation is due. Whether a subscriber has received its data is a separate question, which `apply` answers for the deliveries its own plan owes (step 5, "Deliveries owed"), and which `plan` cannot answer yet (next paragraph).

A snapshot generated and not yet delivered is not measured. The candidate first proposed, comparing the folder named by the distribution agent's last "Delivered snapshot from the '...\<timestamp>\' sub-folder" line (it names the run's folder, `16-snapshot-report-sources` `RS.*.distribution_history`) with the folder of the latest generation, fails on an `immediate_sync` publication: every run makes a new folder that the existing subscriptions never receive, so the two differ for a subscription that awaits nothing (read-only observation, `lab/README.md`, "Observed outside the campaign"). A second candidate, the snapshot commands in `distribution.dbo.MSrepl_commands` (type with the bit `0x80000000`) for one of the subscription's articles beyond the last `xact_seqno` of its distribution agent's history, has a false positive: every scheduled run of `SalesPub` writes new snapshot commands for a subscription that awaits nothing, and the agent's history `xact_seqno` passes them only at its next history write, never while the agent is stopped (read-only observations of the task 12 review and of `lab/README.md`, "Observed outside the campaign"). Proposed, unmeasured: the same test restricted to a window that the distribution agent's own selection uses. In the 2019 source of `sp_MSget_repl_commands` (`stored-procedures/`), the agent takes a snapshot command for a subscribed article when its `xact_seqno` lies between that article's `distribution.dbo.MSsubscriptions.subscription_seqno` and `ss_cplt_seqno`; it also takes header and trailer commands outside that window, so the window is not the whole of what the agent delivers, only what a count needs. A subscription would then await a delivery when one of its articles has snapshot commands in that window beyond the agent's watermark. The watermark is the subscriber's `MSreplication_subscriptions.transaction_timestamp`, the value the agent itself passes to `sp_MSget_repl_commands` as `@last_xact_seqno`, read through a connection to the subscriber where `sqlrepl` has one. The `xact_seqno` of the agent's last history row is only the fallback when the subscriber cannot be reached, and it lags: after a delivery, the history kept the old `xact_seqno` on its "Bulk copied" and "Delivered snapshot" rows for 3.5 minutes, until the agent's next idle row, while the subscriber's `transaction_timestamp` already showed the new value, so the history watermark reported a delivered subscription as awaiting 8 commands, and would have kept doing so had the agent stopped before that idle row (panel Claude, `O2`). Some history rows also carry `xact_seqno` 0x0 (`O2`), and the history cleanup keeps one row per agent (panel Claude, by reading `sp_MShistory_cleanup`). A fallback reading is reported as such, with that lag named. The test reads only the subscription's own `MSsubscriptions` rows (its `agent_id`, `subscriber_id >= 0`), never the rows of a publication: on an `immediate_sync` publication the virtual subscriber `-1` row gets a new window at every scheduled run, and a reader that joined by publication would report every such subscription as awaiting. The `-2` row (anonymous) is updated only while `snapshot_seqno_flag = 0` or its status is 1 or 3 (2019 source of `sp_MSset_snapshot_xact_seqno`): with `allow_anonymous` false it kept its first window across later runs (panel GLM and Claude, `O3`). On an `immediate_sync` publication, a new subscription's window is not written by `sp_addsubscription`: `sp_MSupdate_subscription` copies it from the virtual row when the distribution agent activates the subscription, and copies the window the virtual row holds at that moment, which may be a later run's than the one current when the subscription was added (panel GLM, `O4`: added when run 1 was the only generation, the subscription's window, the history watermark and its "Delivered snapshot" line all named run 2). A subscription whose agent has not activated it yet has no window, so the test treats a subscription row whose `subscription_seqno` or `ss_cplt_seqno` is empty or 0x0 as awaiting a delivery; read without that rule, it would say "awaits nothing" for a subscription that awaits everything. In the same source, the agent delivers snapshot commands only to rows at status 2, and a `concurrent` or `concurrent_c` subscription with an article at status 3 receives nothing until the log reader writes its SYNCDONE token; a pending delivery there may be the log reader's, not the distribution agent's. Measured: on a `concurrent` publication without `immediate_sync`, its log reader stopped and the snapshot generated, the subscription read status 2 and the article its active bit at the publisher (`syssubscriptions`, `sysarticles`), while its rows of `distribution.dbo.MSsubscriptions` were at status 3, the distribution agent logged "The concurrent snapshot for publication ... is not available because it has not been fully generated or the Log Reader Agent is not running to activate it", and the subscriber table did not exist; once the log reader ran, the rows went to 2 and the agent delivered (fix review, `O18`). Status 3 is therefore read in `MSsubscriptions` at the distributor, never in `syssubscriptions`, and it comes before the delivery, not after it. A read-only reading on the lab (`lab/README.md`, same section) found all of `SalesPub`'s scheduled snapshot commands outside its subscription's window, so the restricted test gives "nothing awaited" there whatever the agent's watermark; that reading is one delivered subscription, not the control. The true positives (a generation for a subscription that awaits it, agent stopped; and a subscription added to an `immediate_sync` publication with a ready snapshot and its agent stopped, the `05-snapshot-flag` `S7` path, where no generation happens and activation copies the virtual row's window to the subscription), the subscription not yet activated, and the negative control (an `immediate_sync` publication whose subscription is fully delivered, agent stopped, one more run of the snapshot agent: the test must say nothing is awaited) are campaign item 14. The four panel seats that ran the window with the history watermark found the three named outcomes as expected (`O5`); the subscriber watermark has not been run, so the test stays proposed. Until item 14 has measured it, `plan` cannot see a generated, undelivered snapshot. It reports for each subscription the state of its distribution agent (running, stopped, or its last error since the latest generation), and for a `concurrent` or `concurrent_c` subscription with a row at status 3 in `MSsubscriptions` the state of the publication database's log reader agent, warns when the agent concerned is not running or has failed, and plans nothing for it. `apply` does not rely on this test: step 5 confirms the deliveries its own plan owes from the distribution agent's "Delivered snapshot" lines.

An `immediate_sync` snapshot that is invalid (`immediate_sync_ready = 0`) while no subscription awaits it is not pending: the plan reports it as "full generation deferred to the next run of the snapshot agent" and plans nothing for it. Otherwise the state that `-defer-full-snapshot` leaves would read as pending, `apply` step 5 would start the full generation at once, and the option would cost exactly what it claims to save (review of e220523, three readers). The operations that invalidate a ready snapshot without marking anything leave exactly that state: dropping an article, `alt_snapshot_folder`, `immediate_sync` false, `allow_anonymous` false, and a `sync_method` change between `native`, `character` and `database snapshot` (`15-snapshot-scope` `C.*.droparticle`, `C.*.alt_snapshot_folder`, `C.*.immediate_sync_false`, `C.character.sync_method`, `C.dbsnap.sync_method`, `B.native_anon.1a`, `B.concurrent_anon.1a`: `immediate_sync_ready` 0, every status 2, no inactive article). None of them leaves a subscription without data it had or awaited. Those that leave `immediate_sync` on are costed "full generation deferred": the next run regenerates every article, as `B.*.5b` shows for the deferral. `immediate_sync` false is not: after it, the next run generates only what is awaited (`B.*.3`, the run after `B.*.1b`, generated `m_t3` alone), and the plan costs it "ready snapshot dropped" (see "Publication properties"). The others mark what they invalidate and read as pending: adding an article, an article property, a filter, a view, a column, and a `sync_method` change from or to `concurrent` or `concurrent_c` (`C.*.addarticle`, `C.*.schema_option`, `C.*.articlefilter`, `C.*.articleview`, `C.*.articlecolumn`, `C.native.sync_method`, `C.concurrent.sync_method`, `C.concurrent_c.sync_method`).

The reader keeps apart two kinds of findings that today share one `warnings` list: out-of-scope features (merge, peer-to-peer, updatable or anonymous subscriptions, non-SQL Server peers), for which `plan` refuses the database, and incomplete in-scope objects (a publication without its snapshot agent, a subscription not covering every article of a publication where that cannot exist), which are part of the current state and which the plan repairs. A blanket refusal would block the repair of an interrupted `apply` (panel).

The reader returns an empty current configuration for an instance with no distributor (no `repl_distributor` linked server registered at the publisher), or a database not enabled for publishing (`sys.databases.is_published = 0`), instead of an error (today `readDistributor` fails when the publisher is not registered, panel). That is the starting point of every creation. Those two signals are the only ones: a read that fails is an error, never an absence. A database that is offline, restoring or in standby, a read refused for a missing permission, and a subscriber that cannot be reached stop `plan` with the error, or, for a subscriber, make its preconditions "unchecked" and refuse every operation that runs there; none of them reads as a configuration without that object.

### What a plan is

A plan is an ordered list of operations. Each operation has:

- the object it acts on (distributor, publication, article, subscription, agent, profile) and the kind of change (add, change, drop);
- the property changes it carries, before and after;
- the server and database it runs on, from a table in the code with one measured entry per procedure (`12-contexts` and `distributor-defaults`, rows `X.<procedure>.<database>`): `sp_adddistributor` and `sp_adddistributiondb` in `master` (5001 elsewhere, panel), `sp_addsubscription` and the `sp_add*_agent` procedures of push subscriptions in the publication database at the publisher, the pull procedures in the subscription database at the subscriber, and so on;
- the exact T-SQL, with secrets as named parameters;
- its cost, one or more of: online, start of a pending snapshot, new snapshot, full generation deferred, ready snapshot dropped, reinitialization of named subscriptions, drop and re-add of named subscriptions, subscriber data replaced, subscriber object left behind, shared object changed;
- the reason for that cost, with its source (matrix row, lab row, panel measurement);
- warnings.

The plan as a whole also lists the secrets it needs and whether each is set, the preconditions it checked (subscriber database exists, published table exists and has a primary key for a transactional article, error 14088 otherwise, snapshot folder visible, no subscription declared on a publication declared inactive, error 21000 otherwise), and the agents `apply` will start.

Output: a human summary (one line per operation with its cost, then the totals), `-sql` for the T-SQL, and `-json` for the plan as data, which the GUI and the tests consume. A plan is never saved to be applied later; `apply` always recomputes it. My call.

### Costs and unmeasured changes

The cost of each change, and the flags it needs, come from a cost table in the code, one entry per change and context, each with its source. Only measured entries exist (Rudi's decision). The server asks the flags even for a call that sets a property to the value it already has (`09-snapshot-pub` `SNAP.A22` f01, `SNAPI.A22` f11), so a normalization error does not only fail to converge: it costs a reinitialization at every `apply`. The normalization tests are therefore part of the cost rules. A change that has no measured entry is refused by `plan` with "cost of <change> not measured", never guessed and never sent to the server to find out. The measurement campaign fills the table before the planner is written.

The plan passes exactly the flags the entry says are needed, never both by default.

### Strategies

Each rule comes from a measurement: the analysis, the panel, or a campaign row. The campaign has settled the entries the first version left open; what it did not settle is named in the rule and listed under "Measurement campaign".

The publication properties a strategy depends on (`immediate_sync`, `sync_method`, whether a snapshot is generated) are those in effect when the operation runs: the target values for operations ordered after the publication property changes (step 6 of the order), the current ones before. My call. The same holds for the runtime facts the flags depend on: `plan` computes each call's flags and cost from the state predicted after the earlier operations of the same plan, not from the state observed before it. A step 6 change that invalidates a ready snapshot (a `sync_method` change within `native`, `character` and `database snapshot`, `immediate_sync` false) leaves `immediate_sync_ready = 0` for an `sp_addarticle` of step 8, which then needs no flag (hypothesis, panel, Mistral). Filters and views. The synchronization view is what the snapshot reads; the filter procedure is what the log reader uses. The two must always carry the same clause and column list:

- a row filter is created or changed by `sp_articlefilter @filter_name, @filter_clause`, immediately followed by `sp_articleview @view_name, @filter_clause` with the same clause;
- a row filter is dropped by `sp_articlefilter @filter_clause = NULL`, which drops the filter procedure (panel, second round), immediately followed by `sp_articleview @view_name, @filter_clause = NULL`;
- a column filter (`sp_articlecolumn`) is applied before the `sp_articleview` call. `sp_articlecolumn` rebuilds an existing view by itself when the article has a subscription, at status 1 or 2 (`14-filter-view` `F6s`, `F6u`), and not when it has none (`F6`), even with the reinit flag (`F6r`): the rebuild follows the existence of a subscription, not the flag. The first version cited `F6` as confirming the rebuild; it shows the opposite, on an unsubscribed article. The plan re-issues `sp_articleview` with the article's clause after every column change, which costs nothing and does not depend on that behavior;
- `sp_articleview` is never called without the article's clause: called without `@filter_clause`, it rebuilds the view unfiltered and also sets `sysarticles.filter_clause` to NULL, while the filter procedure keeps filtering the changes (verified after the panel: snapshot unfiltered, changes filtered, export showing no filter; `14-filter-view` `F4`);
- `sp_addarticle @filter_clause` is never generated alone (lab row 12).

Measured on the lab: `sp_articlefilter` with a new clause rewrites the procedure and `filter_clause` but leaves the view on the old clause; with NULL it drops the procedure and also leaves the view (panel, verified twice; `14-filter-view` `F2b`, `F2bs`, `F2bu`, `F3`). ### Order

The order of section 6 of the analysis, extended for creation and corrected by the panel:

1. distributor: create what is missing, skipping what exists (`sp_adddistributor`, run in `master` with `@distributor` (5001 elsewhere, `distributor-defaults` `X.sp_adddistributor.*`), fails with 14099 when a distributor exists, panel; `sp_adddistributiondb` and `sp_adddistpublisher` run from any database), or change it (`sp_changedistributiondb`, `sp_changedistpublisher`);
2. user profiles: create and change;
3. publication database: `sp_replicationdboption publish` (idempotent, panel), log reader agent;
4. drop subscriptions to removed articles, and subscriptions removed from the file;
5. drop removed articles, then removed publications (`sp_droppublication` fails with 14005 while any subscription remains). The drop of a database's last publication also drops that database's log reader agent (`13-transient` `T02`, `T04`, `T06`, `T08`, `T10`: `logreader_after_drop=dropped`, `logreader_agent_left=0`), and the predicted state loses it;
6. change publication properties, in the order of the chains above;
7. change kept articles: properties, then filters and columns, then views, as in "Filters and views";
8. add publications and their snapshot agents, then articles, filters, columns and views. When step 5 has dropped the log reader of a database to which this step adds a publication, the log reader agent is created again first, as in step 3 (whether `sp_addpublication` would create one implicitly is not measured, campaign item 19). Each snapshot agent is disabled as soon as it is created (`apply` step 3);
9. add subscriptions and their agents (push at the publisher, each `sp_addsubscription` followed at once by its `sp_addpushsubscription_agent`, see "Subscriptions"; pull at the publisher and the subscriber), or extend existing subscriptions to new articles;
10. bind agents to profiles, set agent schedules;
11. drop user profiles no agent uses any more.

The builder may refine it; the plan's tests must prove that the order satisfies every dependency measured.

## apply

`sqlrepl apply -f desired.yaml`:

1. recomputes the plan against the live servers, so it never runs a stale plan;
2. prints it, with the count of costly operations, and asks for `yes` (skipped with `-auto-approve`; refused when there is no terminal and no `-auto-approve`);
3. runs the operations in order, each on its server, logging each statement before it runs; all the statements for one server run on one pinned connection (`*sql.Conn`), never on the pool, because the transaction check below is session state. For every publication the plan operates on, before its first operation, `apply` disables that publication's snapshot agent job (`msdb.dbo.sp_update_job @enabled = 0`), and a snapshot agent the plan creates is disabled right after its `sp_addpublication_snapshot`; at the end, whether `apply` succeeds or fails, it restores each job's enabled state as it found it, or enables the jobs it created disabled. No scheduled run then starts inside the plan, which also closes the window between `sp_articlefilter` and `sp_articleview`, where a run would generate the article from the old view (`14-filter-view` `F2b`). A disabled job that is already running keeps running, and `sp_start_job` still starts a disabled job (controller of the third fix round, `O20`, on a plain job; that `sp_startpublication_snapshot` starts a disabled snapshot job is by reading, campaign item 19). So `apply` then waits until the job is idle: while a run generates, the server refuses `sp_addarticle` with 21854 ("a snapshot is being generated", on an `immediate_sync` publication) and `sp_articlefilter` with 21861 ("would deactivate an article in a publication for which a snapshot was being generated", leaving the old filter procedure in place), and `sp_addsubscription` waited 18 s for the run to end (fix review, `O17`). A run started by someone else can still come; when 21854 or 21861 arrives anyway, it is transient for that publication: `apply` rolls back what the call left open (step 4), waits for the run to end, reads `immediate_sync_ready` again, and retries the call once if it still matches the prediction the call's flags rest on. A retry whose flags no longer fit, and a second refusal, are failures. If `apply` dies before restoring a job, the next `plan` sees a disabled snapshot job, compares it with the file (a snapshot agent is enabled unless the file says otherwise) and plans its re-enabling as a difference. `-wait` is one budget for the whole `apply`, from its first operation: the waits for an idle job, the waits before a retry and the wait for the deliveries all count against it, and when it is spent `apply` stops at once with exit code 3, whatever it was waiting for, listing what remains and the deliveries owed so far;
4. after a failed statement, checks `@@TRANCOUNT` on that same connection and rolls back what the procedure left open (lab row 11; a refused `sp_droparticle` leaves two levels open, panel), then stops;
5. on success, starts the snapshot agent of each publication whose snapshot is pending (definition in "Inputs"), then waits, within `-wait` (default 30 minutes, the budget of step 3), for every delivery the plan owes (see "Deliveries owed" below). Once the generation a delivery waits for has ended (at once for an `S7` subscription, which waits for none), `apply` starts the distribution agent job of that subscription with `msdb.dbo.sp_start_job` if it is not running, at the distributor for a push subscription and at the subscriber for a pull one; started earlier, a scheduled or on-demand agent may find no snapshot yet and exit. If the job exits while the delivery is still owed and `-wait` has not expired, `apply` starts it once more, and not again. A shared agent's job is started the same way, which also runs it for the other publications it serves, as its own schedule would. The plan lists those agents among "the agents `apply` will start", and `apply`'s output says which it started. The generation alone is not enough: it sets the statuses and the active bits before and without any delivery. When a publication's snapshot agent job is already running (a run that started before step 3 disabled it, or one someone else started), `apply` does not start it: it waits for that run to end, then starts the agent only if a snapshot is still pending. It reports each delivery confirmed. When `-wait` expires, `apply` exits with exit code 3 (1 is an error, 2 a usage error) and names each subscription still owed a delivery, with its distribution agent's state (job running or not, and its last history line) and, for a subscription with a row at status 3 in `MSsubscriptions`, the state of the publication database's log reader agent. `-wait 0` starts what is pending, waits for nothing, lists every delivery owed as not awaited, and exits with exit code 3 when any is owed. `plan` and `apply` refuse `-wait 0` with `-defer-full-snapshot`, whose step 3 cannot end without the wait and would leave `immediate_sync` off. My call: "the data at the subscriber is what the file describes" is only claimed for what was confirmed.

On failure, `apply` reports what ran, what failed with the server's message, and what remains, and lists the deliveries owed by the operations that completed as "not awaited", as `-wait 0` does, with the exit code of the failure. It does not undo. Running `plan` again reads the server as it is and plans from there; the operations already done are no longer in it, the intermediate states of the strategies are completed (see "Subscriptions"), and a snapshot that a subscription awaits but that was never regenerated is seen as pending in the observed facts (definition in "Inputs"), which gives the plan an operation to start it (panel, second round: otherwise the next plan has nothing left to do and the subscription stays without its data). This is why convergence is a requirement. A failure between `sp_addsubscription` and `sp_addpushsubscription_agent` leaves a subscription whose implicit agent job runs under the Agent service account (see "Subscriptions"); the next plan sees a subscription whose agent properties differ from the file and corrects them. A generated snapshot whose delivery `apply` could not confirm (exit code 3) is not seen by the next plan, which cannot see a generated, undelivered snapshot until campaign item 14 is measured: the next plan has nothing to do for it and reports the state of the distribution agent concerned, as "Inputs" says. The delivery comes when that agent runs; the confirmation was `apply`'s only.

`apply` does not wrap the operations in one transaction: several procedures create jobs, databases or linked servers, some on other servers, and `sp_addsubscription` refuses to run inside a transaction (error 15002, panel).

The panel met a deadlock (1205) during a sequence of subscription drops, and a "only one Log Reader Agent or log-related procedure" message (18752) during `sp_droppublication` and `sp_replicationdboption @value = N'false'` (unpublishing). The panel met 18752 twice under load, with the publication's log reader blocked for over 200 s (panel Claude, `O14`), and the controller reproduced it on an idle lab, two Msg 18752 from `sys.sp_replcmds` while the publication's log reader ran, during the drop of `rv_ctl9a`, whose drop still completed (`O14`). `13-transient` (`T01` to `T10`), on an idle lab, saw neither error in ten create and drop cycles. 18752 comes from the drop of the last publication of a database, which drops its log reader: of eight publications of one database dropped one by one, log reader running, only the last raised it, twice, and the call returned 0 with nothing open and the publication and the log reader agent gone (fix review, one database, `O14`). The controller reproduced it: two messages, the drop completed (`O14`). It is the log reader drop of step 5 of "Order". After an 18752 during a drop, `apply` therefore reads the return code and whether the object is gone: gone, the step has succeeded, with a note naming the message; still there, the rule for 1205 applies. For 1205 `apply` treats the error as a failure, stops, and lets the next `plan` resume; whether a bounded retry is safe is not settled, and the rule stays a stop. My call.

### Deliveries owed

A delivery is owed when an operation of the plan leaves a subscription without data it must receive by a snapshot. `apply` cannot read that from the statuses or the active bits, which the generation sets (see "Inputs"): a subscription added to a ready `immediate_sync` publication read status 2 with its agent stopped and no subscriber table (panel codex directive, `O6`), and with its subscriber database offline and no "Delivered snapshot" line (panel codex neutral, `O6`), and nothing in the pending definition would have made `apply` wait for it. `apply` reads the delivery in the distribution agent's history instead, which names the folder each delivery came from (`16-snapshot-report-sources` `RS.*.distribution_history`, `delivered_line_names_run_folder=yes`). For each delivery owed, `apply` records at the distributor, right after the operation that owes it returns (before the unit, for a push subscription it creates, see "Subscriptions"), a reference time T (the distributor's `SYSDATETIME()`, read on the distributor connection), the mark (the highest `timestamp`, a rowversion, of `distribution.dbo.MSdistribution_history`), the listing of the snapshot root's `unc` folder and of the publication's folder in it, and whether the publication's snapshot agent job is running. The deliveries owed, by operation:

- a subscription the plan creates, push or pull, with `initialization` by snapshot, re-additions of the drop and re-add strategies included: all its articles; T before its `sp_addsubscription` for a push subscription, after it at the publisher for a pull subscription. A subscription initialized by "replication support only", backup or LSN is owed nothing;
- an article added to existing subscriptions: on an `immediate_sync` publication, every subscription `sp_addarticle` has subscribed, T after `sp_addarticle`; otherwise every subscription extended to it, T after the extension. The completion of an intermediate subscription by `@article = 'all'` is the same case;
- an operation that marks rows for reinitialization (a change whose cost entry is a reinitialization, a `sync_method` change from, to or within the concurrent family included): the subscriptions with a row that the call moved from status 2 to status 1, read before and after the call on the same connection; T after the call;
- a snapshot pending before the plan, which step 5 starts: the subscriptions that read as pending when `apply` recomputed the plan; T at that reading;
- step 3 of `-defer-full-snapshot`: every subscription extended in step 2, for the new article; T after the extension.

Operations whose cost is "full generation deferred" or "ready snapshot dropped", drops, and online changes owe nothing.

A delivery owed is confirmed by a row of `distribution.dbo.MSdistribution_history` at the distributor, from the subscription's distribution agent (its `MSdistribution_agents` row; for a subscription on a shared agent, the shared agent stored with `publication = N'ALL'`), that meets three conditions: its rowversion is above the mark, its `time` is at or after T (both on the distributor's clock: `sp_MSadd_distribution_history` writes `time` with `GETDATE()`), and its `comments` read "Delivered snapshot from the 'unc\<name>\<timestamp>\' sub-folder in n milliseconds", where `<name>` is the publication's folder and `<timestamp>` an accepted run folder (below). The rowversion alone is not enough. `sp_MSadd_distribution_history` rewrites the agent's last history row in place, its comments, time and rowversion with it, when that row is updateable and the new message is idle, or asks to update the row and both messages are idle or in progress (2019 source in `stored-procedures/`). A row written before the mark can therefore come back above it with a new text, and a "Delivered snapshot" row may be overwritten by the agent's next message. `apply` therefore polls the history every second (every 250 ms while a report samples), keeps each "Delivered snapshot" line it has seen with its text and time, and confirms from what it kept. Proposed, from the source: whether a "Delivered snapshot" row is ever rewritten in place is campaign item 14.

The publication's folder name is never composed from the server, database and publication names: on a named instance the server part is not `@@SERVERNAME` as it stands (by reading; unmeasured, campaign item 14). `apply` reads the name from what the publication's own agents wrote: the "Delivered snapshot" line of any subscription of the publication, or, before any delivery, the folder under the snapshot root (`<alt_snapshot_folder or working_directory>/unc/`) in which a run folder appears during a run of that publication's snapshot agent; names are compared case-insensitively. The line holds that relative `unc\` path whatever the folder: with `alt_snapshot_folder` set, it still read `unc\REPLLAB_RV_Q7X2KD_P_RV_Q7X2KD_AL\20261111162904\` while the files were under the alternate folder, and a space in a publication name is kept (fix review, `O19`). When no folder, or more than one, can be tied to the publication, its deliveries are reported unconfirmed. A shared agent's line names the folder too (`RS.native.distribution_history`, `agent=shared`), and `<name>` names the publication; a shared agent serves one subscriber database, which has at most one subscription to a publication, so the publication and the agent identify the subscription. The mark excludes every line written before T, those of an earlier incarnation of the same subscription on a shared agent included. Under `concurrent` and `concurrent_c` the line is not enough: the delivery stays owed until the subscription's rows of `MSsubscriptions` are at status 2 as well, since status 3 there means the subscription waits for the log reader's SYNCDONE token ("Inputs"; fix review, `O18`).

The run folder accepted depends on the subscription. For a subscription the plan creates, `apply` reads its status on the first statement after the push unit (after `sp_addsubscription` at the publisher for a pull subscription), never between the unit's two calls; `plan` predicts that status from the plan-time state and says in its output that it is a prediction, and `apply`'s wait uses the status read after the unit. A non-`S7` subscription cannot reach status 2 inside the unit without a run that started after T, whose folder counts anyway.

- A subscription the plan creates that is at status 2 after the unit (an `immediate_sync` publication with a ready snapshot, the `05-snapshot-flag` `S7` path, where no generation happens): any run folder of the publication. The agent activates the subscription from the run the virtual row holds at that moment, which may be later than the run current at T (panel GLM, `O4`), and the subscription did not exist before T, so any delivery after the mark is its initial one.
- Any other delivery owed: a run folder generated after T, found by listing the publication's folder, never by comparing a folder's name with a clock. A folder is generated after T when it is absent from the listing taken at T and does not belong to a run that was in progress at T. When the snapshot job was running at T, `apply` lists the folder again when that run ends: a folder absent at T and present then is that run's, and counts only if, once the run has ended, every row the delivery concerns reads as generated (status 2 and the active bit; for the concurrent family, `MSsubscriptions` as above); a folder that appears after that second listing counts as generated after T. With the publication's snapshot job disabled (step 3), the runs after T are those `apply` starts once the job is idle, and any run someone else starts. When the publication's folder cannot be listed (an alternate or UNC folder the distributor cannot read), the delivery is unconfirmed: `apply` exits with exit code 3 and says that the snapshot folder, which it names, could not be listed.

An older folder is never accepted for those: an agent stopped before the plan may deliver after T a snapshot generated before it, which does not hold what the plan owes.

The confirmation is per subscription. The "Bulk copied data into table" and "Applied script" lines of the same delivery are reported per article (see "The report"), not required: whether an empty table or a schema-only article writes such a line is not measured. A pull subscription's agent has its row at the distributor (`08-pull` `P1.named`, `distributor_agent`), and `apply` reads its history there; that a pull agent writes the "Delivered snapshot" line to the distributor's history is not measured (campaign item 14), and until it is, a pull subscription whose line does not come is reported as unconfirmed with the state of its agent job at the subscriber.

This rule rests on the measured line and folder (`RS.*.distribution_history`), the `S7` activation (`O4`), status 3 under the concurrent family (`O18`) and the relative path of the line (`O19`). The cases it names beyond those, the run in progress at T, the in-place rewrite of a history row, the shared agent's re-added subscription, the pull agent and the folder name on a named instance, are reading, and campaign item 14 measures them.

### Blocking

Three things decide how a snapshot blocks writers on the published tables: the publication's `sync_method` (how long), `immediate_sync` (which tables), and the schedule of its snapshot agent (how often). The measurements come from the review of e220523 (five readers, a writer updating one row in a loop during a generation) and from `15-snapshot-scope` phase A, where writers update one row every 50 ms on every table during the run.

- The lock covers only the tables the run generates: every table of the publication under `immediate_sync`, which generates every article (`A.imm.*`), the new table alone without it (`A.non.native`: `m_t3` waited 3141 ms, `m_t1` and `m_t2` 16 ms).
- `native` and `character` lock the generated tables together, not each while it is copied. In the review, a writer on a 100-row table copied in 40 ms waited 4.6 s, as long as the writer on the 1M-row table; in `A.imm.native` and `A.imm.character` the writers of the two tables waited alike and at the same time (`t2_vs_t1=similar`, `overlap_t1_t2=yes`), `character` as `native`. The lock ends with the snapshot history's last line (`t1_ends_at_gen_end=yes`) and covered between a third and two thirds of the history's duration in these runs: 2044 ms of 3990 under `native`, 3002 of 4920 under `character`, 3141 of 5290 for the one table of `A.non.native`, 1235 of 3220 for that of `A.non.character`. The history says "Locking published tables while generating the snapshot", but its times are the times the agent wrote the rows, not the times of the events: its lines come in bursts a few milliseconds apart, and under `database snapshot` the writers were released 600 ms before the Locking line was written (`A.imm.dbsnap`). No step of `apply` and no figure of the report is placed by a history line other than the first and the last, and the last line does not bound the writers' stalls under `concurrent_c` (next item).
- `concurrent` and `concurrent_c` lock briefly near the start and near the end. Near the start: under `concurrent` the writers of the existing tables waited 62 and 70 ms at +416 to +487 ms (`A.non.concurrent`), under `concurrent_c` about 50 ms on every table, ending 1.3 s before the run's first history line (`A.non.concurrent_c`), and a 50 ms lock sampler saw 68 to 260 ms of `LCK_M_IX` waits on the published tables near the start of two `concurrent_c` runs, before the first bulk copy line, blocked by the snapshot job's session (panel Claude, `O12`). Near the end: under `concurrent` the writers waited about 100 ms at the end of the run (`A.imm.concurrent`, from +4655 to +4751 ms of a 4757 ms run), and the same sampler saw 72 to 97 ms of lock waits just before the last history line of both `concurrent_c` runs (panel Claude, `O12`). Under `concurrent_c` the campaign also measured a 207 ms stall on all three tables together after the run's last history line, from +7196 to +7403 ms of a 5303 ms run, about 1.9 s later (`A.imm.concurrent_c`). That figure is the writers' longest `UPDATE`, not a sampled lock wait: a stall of the same kind, 252 to 284 ms on both tables 4.9 s after the last line, showed no lock wait to the 50 ms sampler (panel Claude, `O12`), and under load a writer's longest `UPDATE` ended 8.4 s after the last line (panel Mistral, `O12`, a 939 ms `UPDATE` on a container the other seats were loading). What these late stalls wait on is not known; campaign item 18 measures it. The review measured 0.1 to 1 s. Under `concurrent` the writer's longest UPDATE took 101 ms, of which 24 ms were lock wait; the rest was not a lock wait (a development run of task 11b saw `WRITELOG`) (`16-snapshot-report-sources` `RS.concurrent.sampling_250ms`). They exist for transactional publications only, and are refused on a snapshot publication with 22547 (`09-snapshot-pub` `SNAP.P12`).
- `database snapshot` and `database snapshot character` read a database snapshot. Writers wait about 200 ms near the start, while the database snapshot is created, and not after: `A.imm.dbsnap` 211 ms, `F.imm_dbsnap_1` to `_3` 109 to 195 ms, `A.non.dbsnap` 321 ms on the new table (the review: under 0.6 s, under 0.2 s on most runs). `database snapshot character` is not measured. They need the Enterprise or Developer edition, which `plan` checks as a precondition. They store `sync_method` 5 and 6. Today the export decodes these as `unknown(5)` and `unknown(6)` (`internal/decode`, `syncMethods`), so plan 2 adds both codes to the code table before the planner compares them.
- An `immediate_sync` publication generates every article at every run of its snapshot agent. The default schedule runs it every 5 minutes, so under `native` the generated tables are blocked for the locked part of each generation every 5 minutes, whatever the plan does (lab: SalesPub, 12 full generations in an hour).

Any other pair is refused with "cost of <change> not measured": the server accepted `native` to `database snapshot` with no flag (panel Mistral, `O10`), but the cost of the snapshot that follows is not measured, campaign item 18. The first version of this section called every `sync_method` change a reinitialization; the rows above contradict it.

### The report

Every snapshot that `apply` starts (step 5, and the "generate and wait" operation of `-defer-full-snapshot`) produces a report, and so does every snapshot that `sqlrepl snapshot -publication <name>` starts. That command starts the snapshot agent of one publication, waits like `apply` (`-wait`), and writes the report. It changes no configuration, so it needs no plan.

A run waits for the deliveries it owes, not for one per subscription. For `apply`, those are the deliveries owed of "Deliveries owed" that the run serves; for `sqlrepl snapshot`, the subscriptions of the publication that read as pending at the mark, each confirmed by a "Delivered snapshot" line naming a folder generated after the mark, by the same rule. A full generation on an `immediate_sync` publication delivers nothing to subscriptions that already have their data (`15-snapshot-scope` `B.*.5b`, `delivered(existing)=[](no_delivery)`, and `D.imm_native.snapshot2`), so a run that owes no delivery ends with its generation, plus the sampling tail (see "blocking" below); otherwise every such run would wait until `-wait` and be marked incomplete (hypothesis, panel, Claude and codex neutral).

The report is written only once the sampling has ended (see "blocking" below) or the wait has timed out, so it never shows a figure that can still change. A delivery owed that never comes, such as the `database snapshot` failure of campaign item 17, keeps the sampler running until `-wait` expires. A timed-out run gives a report marked incomplete, with what was collected. `-wait 0` writes no report, and `sqlrepl snapshot` refuses `-wait 0`.

The report is one self-contained HTML file (no external script, style or font, so it can be mailed or attached), next to a JSON file with the same data, which the GUI reads later. The path is set with `-report <path>`; by default it is `snapshot-<publication>-<UTC timestamp>.html` in the current directory.

Starting the agent is checked through the return code. When the job is already running, `sp_startpublication_snapshot` refuses, but raises no error that TRY...CATCH sees, and `@@ERROR` stays 0: only the return code is 1 (review of e220523; `16-snapshot-report-sources` `RS.*.start_running`, under the three methods measured). The only message is an informational "HResult 0x5606, Level 16, State 1" line followed by the Agent's "Request to run job ... refused because the job is already running", not a `Msg` line, so a client that only watches for errors sees nothing. `sqlrepl` therefore checks that the agent's job is not running before it takes its mark. `sqlrepl snapshot` refuses with "snapshot agent already running" when it is; `apply` step 5 waits for that run to end instead, starts its own only when a snapshot is still pending, and writes no report for a run it did not start. Both treat a non-zero return code as a failed start. Without these checks, the report would describe a run `sqlrepl` did not start.

What the report holds, and where each value comes from:

- the run: publication, `sync_method`, the edition, and the start and end of the generation and of each subscription's delivery. These come from the snapshot and distribution agent history after a mark taken before the start. For a publication without an independent agent, the delivery rows belong to the shared agent (`publication = 'ALL'`); they are attributed to the publication through the run folder named in the "Delivered snapshot from the '...' sub-folder" line, which names it for a shared agent too (`RS.native.distribution_history`, `agent=shared`). Only the first and the last history lines place the generation in time (see "Blocking"), and they are write times too: the agent writes its history in bursts, so the start and end of the run may lag the events they stand for, under load by more than the sampling interval, and the report says so next to the run times, as it does for the per-article times (hypothesis, panel, Mistral).
- per article: the rows bulk copied and the time it took at each subscriber. The distribution history writes one "Bulk copied data into table" line per bcp partition, naming the destination table: the report sums the lines and maps each destination table back to its article through `dest_table`. The sums equal the source row counts (`RS.*.distribution_history`, `bulk_sums_match=yes`). The snapshot history has per-article bulk copy and schema lines under every method measured, `concurrent` included (`RS.*.snapshot_history`, `per_article_lines=yes`; `15-snapshot-scope` `A.imm.concurrent`); the review of e220523 had seen none under `concurrent`, and the first version of this section followed it. Their times are write times, so a per-article generation time read from them is approximate, and the report says so.
- the files of the run, with their size, and the total for the run's folder, read on the distributor with `sys.dm_os_enumerate_filesystem`. This works for the default folder, for a sysadmin and for a login with only `public` at the server and `SELECT` in the distribution database, which see the same files and bytes as `find` (`RS.*.filesystem_sa`, `RS.*.filesystem_low`). An alternate or UNC folder the distributor cannot list is reported as not readable, never guessed.
- blocking: the sessions that waited on a lock held by the snapshot agent, and the sessions the agent waited on, with the object, the wait type and the longest wait. They are sampled on the publisher from `sys.dm_exec_requests` (with `blocking_session_id`) and `sys.dm_os_waiting_tasks`, from the mark until the later of two moments: the end of the last delivery the run owes (above; the generation's end when it owes none), and a tail after the snapshot history's last line. The tail is a flag, `-sample-tail`, default 10 s, taken by `sqlrepl snapshot` and by `apply` (for the reports it writes, step 5 and the deferral's step 3); the report shows it next to the sampling interval. A tail, not a test of when the lock is gone, is the choice: a sampler that waited for the lock to go would have to know which session holds it, which the `program_name` rules below cannot always tell. The tail is not a bound. The late `concurrent_c` stall of the campaign, 2.1 s after the last line (`15-snapshot-scope` `A.imm.concurrent_c`, +7403 ms in a 5303 ms run), was the writers' longest `UPDATE`, not a sampled lock, and a 50 ms lock sampler saw no lock wait in a stall of the same kind 4.9 s after the last line (panel Claude, `O12`); under load, a writer's longest `UPDATE` ended 8.4 s after the last line (panel Mistral, `O12`). The `concurrent_c` locks the panel's sampler did see fell inside the run, held by the snapshot job's session, which the attribution rules below cover (panel Claude, `O12`). Item 18 measures both the lock waits and the stalls after the last line, and the default tail with them. A late lock whose holder carries no name the attribution rules below know is listed as unattributed.
  - Which sessions belong to the agent (`RS.*.program_names`, sampled every 250 ms, so a lower bound). The snapshot agent's sessions carry the snapshot job's name, which equals `MSsnapshot_agents.name`, `SQLAgent - TSQL JobStep (Job <job id> : Step n)`, "Snapshot Agent Distributor Connection for publication '<server>:<database>:<publication>'", "Snapshot Agent History Connection for publication ...", "Snapshot BCP thread #n for publication <name>", and under `database snapshot` "Database snapshot creation connection for publication <name>". "Snapshot Agent Smo Connection" names no publication and cannot be attributed. An independent distribution agent's sessions are named `<instance>_<publisher_db>_<publication>`; a shared one's `<instance>_<publisher_db>` (`repllab_Sales`), which cannot be tied to a publication by `program_name`. The writer's blocker was the session named after the snapshot job under `native` and `database snapshot` (`writer_blocked_by=[<snapshot_job>]`); under `concurrent` no blocker was seen, the lock being shorter than the sampling interval. The report attributes a session to the run by the job name or the publication name it carries, and lists the others as unattributed.
  - Sampling misses waits. Compared with the writer's own lock wait: at 1 s, the 2462 ms wait under `native` read as 1554 ms and the 289 ms wait under `database snapshot` was missed; at 250 ms they read as 2376 ms and 36 ms (`RS.native.sampling_1s`, `RS.native.sampling_250ms`, `RS.dbsnap.sampling_1s`, `RS.dbsnap.sampling_250ms`). The review had seen the same at 1 s (a 1.6 s wait missed, a 4.6 s wait read as 3.8 s). The report samples every 250 ms, states the interval, says that the longest wait it shows is a lower bound, and that a wait shorter than the interval may not be seen at all.
  - Permission. The sampling needs `VIEW SERVER PERFORMANCE STATE` on 2022 (`VIEW SERVER STATE` before 2022): without it, `sys.dm_os_waiting_tasks` fails with error 300, while `sys.dm_exec_requests` raises no error and returns the caller's own session only (`RS.m_low.waiting_tasks`, `RS.m_low.exec_requests`), so the check reads the permission itself, not an error. `sqlrepl snapshot` and `plan` check it before the start. Without it, the report says the blocking was not collected, and the snapshot still runs.
  - No server option is changed. The report does not use the `blocked_process_report` event, which needs the server option `blocked process threshold` and an event session. `sqlrepl` never changes a server option or creates a server object for a report. My call.
- agent errors and retries during the run (agent history, `MSrepl_errors` after the mark).

Apart from the snapshot itself, the report only reads from the servers. Its sources are measured under `native`, `concurrent` and `database snapshot` by `16-snapshot-report-sources` (campaign item 13); `character` and `concurrent_c` are taken to read like `native` and `concurrent`, which their history lines in `15-snapshot-scope` support (`A.imm.character`, `A.imm.concurrent_c`: per-article lines present).

## Secrets

The file holds no secret. A password appears as a `password_secret` name. At `plan` and `apply` time, `sqlrepl` reads the value from the environment variable of that name, after loading an optional `.env` file (default `./.env`, `-env` flag), where the real environment wins. The loader is the stdlib-only `internal/dotenv` of `~/Sources/Repos/atelier/outils/sylloge/internal/dotenv/`, copied, not imported. `plan` reports every secret the plan needs and whether it is set; `apply` refuses to start while one is missing.

The model gains a secret name for every password parameter of every in-scope procedure, which the builder lists from `sys.all_parameters`; among those it lacks today (panel): the job account (`@job_login`, `@job_password`) of every agent, the distributor credentials of a pull agent (`@distributor_login`, `@distributor_password`), the `distributor_admin` password of a remote distributor (`sp_adddistributor @password`), the SQL login of `sp_adddistributiondb` when `@security_mode = 0` (error 21694 otherwise), the distributor credentials of the snapshot agent (`sp_addpublication_snapshot @distributor_login`, `@distributor_password`), and those already named (subscriber, publisher, `MSdistpublishers`, FTP).

Secrets never appear in the T-SQL that is printed or logged. `apply` passes them as parameters of `sp_executesql`; `plan -sql` prints the same statement with the parameter names and a comment naming the secret, so the printed text is the executed text without the values. My call.

Passwords are set when an object is created. `plan` cannot read them, so it never plans a password change; `apply -rotate-secret NAME` changes the password of every object that uses that secret, as an explicit action. My call.

## Servers and connections

Servers are named in the file by their SQL Server name (`@@SERVERNAME`), which is what replication stores and may not resolve from where `sqlrepl` runs (the lab's `REPLLAB`). How `sqlrepl` reaches each server, and with which credentials, is given at run time, never in the file: the builder chooses between flags (`-server REPLLAB=tcp:127.0.0.1,11980`) and a connections file kept outside the repository. `sqlrepl` connects to the publisher, the distributor, and each subscriber that has a pull subscription or whose database must be checked.

## Engine as a library

The GUI will drive the same engine. Constraints on the builder:

- the comparison and the plan are pure functions of the desired configuration, the current configuration, the observed runtime facts and the cost table, with no database access, so that the GUI can recompute costs on every edit and the tests can cover them without a server;
- reading the servers, computing the plan, and executing it are separate packages;
- the plan is a Go value that serializes to JSON without loss; `-json` and the GUI use the same serialization;
- the CLI only parses flags and prints.

## Extending the model and the export

The model covers every parameter of the in-scope procedures (Rudi's decision), so that "whole truth" holds down to properties: among others `allow_partition_switch`, `replicate_partition_switch`, `enabled_for_het_sub`, `enabled_for_internet`, the distribution database file locations and sizes, the initialization parameters (backup device and location, LSN), the secret names above. The builder lists the parameters of each procedure from `sys.all_parameters` on each supported version and maps each to a field or to a documented exclusion.

The export must read what the plan manages, since the plan compares against it:

- an instance with no replication, as an empty configuration;
- pull subscriptions: at the publisher (`syssubscriptions.subscription_type = 1`) and at the subscriber, where the agent's settings are in `MSsubscription_properties` and `MSreplication_subscriptions` is written by `sp_addpullsubscription`, not by the agent (panel); today the export warns and skips them, so no plan on a database that has one could converge (panel);
- snapshot publications (`repl_freq = 1`): today reported under `warnings`;
- every profile of the distributor and its use by the agents of every database;
- the observed runtime facts the planner takes as input ("Inputs"), the state of each distribution agent included;
- the definition of each synchronization view, enough to check it against the clause and the columns.
- a read that returns NULL because of metadata visibility is reported, not exported as empty: today the agent jobs' run-as account is read through a `LEFT JOIN sys.credentials` with `ISNULL(..., N'')` (`internal/reader/queries.go`), so under a login without `VIEW ANY DEFINITION` a job that runs under a proxy is exported with an empty account, and `plan` would then see a job account change on every such agent; plan 2 reads the proxy and reports a credential it cannot see.

## Testing

- Unit tests for the normalization, the comparison, the cost table and the ordering, with configurations built in Go; no server.
- Integration tests on the lab container, gated by an environment variable like `TestQueriesParse`. The central scenario: start from an instance with no replication, apply a file, export, check that the export normalizes to the file and that `plan` is empty. Then a set of change scenarios, one per strategy above, each checking the plan's operations and costs before applying, and convergence after.
- For every scenario that touches a filter or columns, the test also checks the data: after the snapshot and after changes made at the publisher, the subscriber holds exactly the rows and columns the file describes. The export cannot see a synchronization view out of step with its filter (panel), so convergence of the configuration alone does not prove it.
- The integration tests run on the 2019, 2022 and 2025 images before the support claim holds.
- Each strategy and each cost entry has a test that fails when the rule is broken. The builder breaks each rule once to watch its test fail.
